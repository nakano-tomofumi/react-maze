# Development workflow

このリポジトリでは、開発タスクと変更履歴を GitHub Issue / Pull Request に集約する。

## Issue

- 開発タスク、要件、検討事項、実装方針、未解決事項は GitHub Issue を一次情報とする。
- 実装前に要件、影響範囲、依存関係、完了条件を確認する。
- 独立して完了できる作業は別 Issue に分割する。
- 同一目的でも変更量が大きい場合は複数 PR に分割してよい。

## Pull Request

Issue に基づくコードまたはドキュメント変更は、原則として専用ブランチから Pull Request を作成する。

PR には以下を記載する。

- 変更内容
- 検証内容と結果
- 関連する Issue

Issue を完了する PR では `Closes #<issue-number>` を使用する。複数 PR に分割した場合は、Issue を完了する最後の PR のみ `Closes` を付け、それ以前の PR は `Refs #<issue-number>` などで関連付ける。

レビュー指摘は根本原因まで修正し、類似箇所、副作用、未検出の問題がないか確認する。必要に応じて再発防止のテストを追加する。

## 変更範囲

- 既存のコードスタイルと構成に合わせる。
- 変更範囲は目的達成に必要な範囲に限定する。
- ユーザーが明示的に求めない限り、無関係な変更や大規模なリファクタリングを同じ PR に混在させない。

## 検証

変更後は、変更内容に応じてテスト、ビルド、型チェック、lint、その他の妥当な検証を実行し、結果を PR に記載する。

実行できなかった検証がある場合は、その内容と理由を明記する。

## ドキュメント運用

リポジトリ内の `docs/` には、現在も継続して参照する仕様、設計判断、開発・運用ルール、環境や検証手順を置く。

次のような一時的・履歴的な情報は、原則として `docs/` に残さない。

- 個別 Issue の実装経緯
- PR ごとの変更履歴
- 作業中の TODO や進捗メモ
- 過去の検討過程
- 一時的な移行手順
- 既に完了した開発計画
- Issue / PR / commit history から復元できる情報

一方で、開発中に生まれた判断が現在も有効な設計・運用ルールになった場合は、必要に応じて恒久ドキュメントへ反映する。

README はプロジェクト概要とクイックスタートを担い、詳細な開発ポリシーは `AGENTS.md` と `docs/` に置く。同じ説明を長文で重複させず、必要に応じてリンクで誘導する。
